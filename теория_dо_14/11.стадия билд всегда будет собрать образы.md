Хороший вопрос — разберём, потому что это ключевой момент для понимания CI/CD.

## Короткий ответ

**При каждом пуше будет собирать заново.** Все 8 образов, каждый раз. Это поведение по умолчанию.

## Почему так

Логика CI/CD простая: ты пушишь код → пайплайн собирает образы из **этого** кода → деплоит **эти** образы. Если пайплайн пропустит сборку — он задеплоит старые образы, в которых нет твоих свежих изменений. Поэтому build идёт каждый раз.

И каждый раз тег образа разный — у тебя в пайплайне:
```yaml
IMAGE_TAG: "$CI_COMMIT_SHORT_SHA"
```
То есть тег = короткий хэш коммита. Каждый коммит = новые теги = новые образы в Docker Hub.

## Сколько времени это занимает

Для твоего проекта (8 сервисов, Java + Python + Node):

- **Первый раз:** ~15–20 минут на всё (Maven скачивает зависимости, Docker слои собираются с нуля).
- **Каждый следующий раз:** примерно столько же, потому что **Kaniko по умолчанию не использует кэш**. Каждый build-под запускается с нуля.

Это раздражает, особенно если ты правишь только один сервис, а пересобираются все 8.

## Как сделать умнее (если захочешь)

Есть три уровня оптимизации, по возрастанию сложности:

### Уровень 1. Собирать только то, что менялось (правила `changes:`)

Добавить в каждый `parallel:matrix` правило: «пересобирай этот сервис, только если в его папке что-то изменилось».

```yaml
build:
  rules:
    - changes:
        - src/bank-of-anthos/src/frontend/**/*
  # ...
```

Минус: с `parallel:matrix` это работает криво, надо разбивать на отдельные джобы для каждого сервиса. Многословно.

### Уровень 2. Включить Kaniko cache

Kaniko умеет кэшировать слои образов в самом Docker Hub. Добавляешь флаги:

```
--cache=true
--cache-repo=docker.io/$DOCKERHUB_USER/cache
```

Тогда повторная сборка того же сервиса без изменений = пара секунд (берёт из кэша). Maven-зависимости тоже закэшируются.

### Уровень 3. Собирать только при изменении конкретных путей

Комбинация Уровней 1 и 2. Идеал, но писать много YAML.

## Что делать сейчас

**Для школьного проекта — оставить как есть.** Build пересобирает всё, это занимает 15–20 минут, проверяющего это устраивает. Главное — чтобы пайплайн **проходил**.

Когда сдашь и захочется красиво — добавим кэш Kaniko (минут 10 работы). Сейчас не отвлекайся.

## Один полезный лайфхак

Если хочешь повторно гонять пайплайн без новых пушей (например, проверить, что staging работает) — в GitLab UI можно нажать **«Retry»** или **«Run pipeline»** на любом коммите. Это **не будет** пересобирать образы заново, если ты используешь Retry на конкретной задаче, — он просто перезапустит её. Но Run pipeline = новый запуск с нуля.
