## Что такое BuildKit и почему он «хочет root»

Чтобы собрать Docker-образ, нужно создавать слои файловой системы, монтировать их, иногда делать `chroot` (смена корневой папки) — это операции, которые в Linux требуют либо root-прав, либо специальной возможности `CAP_SYS_ADMIN`. Поэтому традиционно BuildKit/Docker-демон работают с привилегиями.

В Kubernetes привилегированный контейнер = почти то же самое, что root на хост-машине. Если злоумышленник захватит такой под — он сможет вырваться из контейнера на ноду. Это и есть проблема безопасности, которую ты заметил.

## Путь 1: один BuildKit-Deployment в кластере (твой текущий подход)

**Как работает:** ставится один привилегированный под `buildkitd`, висит постоянно, к нему по сети `tcp://...` подключаются `buildctl`-клиенты из job'ов.

| Плюсы | Минусы |
|---|---|
| Быстро: при каждом билде не надо поднимать BuildKit заново | Один привилегированный под висит 24/7 — постоянная угроза безопасности |
| Кэш слоёв сохраняется между билдами (важно для скорости) | SPOF: упал buildkitd — встал весь CI |
| Просто настроить | Нужно отдельно следить за его обновлением |

## Путь 2: BuildKit как sidecar в каждом job'е

**Как работает:** в `.gitlab-ci.yml` указываешь `services: [moby/buildkit:rootless]`, и GitLab Runner на каждый билд поднимает свежий BuildKit-контейнер прямо в job-поде. После билда — удаляется вместе с job'ом.

| Плюсы | Минусы |
|---|---|
| **Эфемерность** (контейнер живёт ровно билд) — меньше окно атаки | Нет общего кэша между билдами → медленнее |
| Изоляция по job: один билд не видит другие | Чуть сложнее конфиг |
| Есть **rootless-режим** — BuildKit работает без root-привилегий (через user namespaces) | Rootless иногда падает на хитрых Dockerfile (редко, но бывает) |

## Что принято в продакшене

В современном production-DevOps **тренд — путь 2 с rootless** (или Kaniko, который изначально rootless). Принципы:

1. **Эфемерность** — каждый билд изолирован, после билда ничего не остаётся.
2. **Least privilege** (наименьшие привилегии) — никаких висящих привилегированных подов.
3. **Zero trust в кластере** — не доверяй сетевым соседям.

Google, GitLab, CNCF в своих рекомендациях — все за rootless-builders в job-локальном режиме.

**НО:** для твоей задачи (учебный пайплайн, нужно сдать) и для требований Василия (он сказал «BuildKit») — оба пути валидны. Разница в скорости и в красоте архитектуры.

## Моя рекомендация для тебя

**Идём по Пути 2 (rootless BuildKit как sidecar).** Причины:

1. **Не нужно лезть в чужой кластер** с Deployment'ом BuildKit — все правки только в `.gitlab-ci.yml`. Минимум вмешательства в инфру Василия.
2. **Меньше точек отказа** — нет долгоживущего демона, который может умереть.
3. **Это «правильно» с точки зрения безопасности** — будет хороший аргумент на пир-проверке («я отказался от привилегированного демона, потому что…»).
4. **Перенос проще** — твой будущий код будет работать в любом GitLab Runner с Kubernetes executor, без зависимости от наличия buildkitd-сервиса.

Минус — каждый билд будет на 30-60 секунд медленнее из-за отсутствия общего кэша. Для учебного пайплайна некритично.

Прогресс есть — раннер уже использует `moby/buildkit:rootless`, образ скачался, скрипт запустился. Но buildkitd упал на старте:

```
[rootlesskit:child ] error: failed to share mount point: /: permission denied
[rootlesskit:parent] error: child exited: exit status 1
```

## В чём проблема

Rootless BuildKit использует **user namespaces** (механизм Linux: даёт процессу «свой» root внутри неймспейса, но без реальных привилегий на хосте). Для этого ему нужны **расширенные возможности** (Linux capabilities) — конкретно `SETUID`, `SETGID`, и возможность делать mount внутри своего неймспейса.

GitLab Runner на Kubernetes по умолчанию запускает job-под с **сильно ограниченным securityContext** — поэтому rootless BuildKit не может создать свой user namespace и падает.

## Как чинить

Есть два пути:

**Путь А: попросить Runner поднять под с нужными возможностями.** Это делается через `services:` или через `[runners.kubernetes.pod_security_context]` в конфиге раннера. Сложно — лезть в конфиг раннера.

**Путь Б: использовать другой rootless-режим, без user namespaces.** В образе `moby/buildkit:rootless` есть переменная `BUILDKITD_FLAGS`, куда можно добавить флаги для запуска без шарения mount-точек. И запускать buildkitd через специальный entrypoint, который обходит ограничения. 

**Путь В (самый простой и проверенный):** использовать образ `moby/buildkit:latest` (не rootless) + флаг `--oci-worker-no-process-sandbox`. Запуск будет работать в любом securityContext, но контейнер будет root. Безопасности меньше, но Василий и просил BuildKit, не Kaniko-rootless.

### Гибридный подход: nonroot buildkit + флаги обхода

В образе `moby/buildkit:rootless` пользователь не-root (`user 1000`), но есть способ запустить buildkitd без `rootlesskit` — напрямую с флагами, которые отключают sandbox. Это снимает требование к user namespaces.

Меняем в `before_script`:

```bash
# Запуск buildkitd напрямую (не через rootlesskit), без OCI-sandbox
buildkitd \
  --oci-worker-no-process-sandbox \
  --rootless \
  --addr unix:///tmp/buildkitd.sock &
```

И в `script` добавляем `--addr unix:///tmp/buildkitd.sock` к `buildctl`.

Но это всё равно может упасть на permission denied для других mount-операций.

## Самое прагматичное решение прямо сейчас

Давай **откатим rootless и пойдём через привилегированный режим** — но не как у тебя на ноуте (отдельный Deployment), а **`moby/buildkit:latest` прямо в job-поде**. Минусы:
1. Под будет привилегированный — Runner должен это разрешить.
2. Это менее безопасно.

Но это **точно заработает** и Василий получит BuildKit, как просил.

**Проблема:** GitLab Runner по умолчанию не даёт job-подам `privileged: true`. Это разрешается через ConfigMap раннера флагом `privileged = true` в `[runners.kubernetes]`. Снова лезть в configmap.
