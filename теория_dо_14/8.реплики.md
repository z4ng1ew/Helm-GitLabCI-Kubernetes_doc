## Реплики

### На staging
Сейчас по 1 на сервис (как в `values.yaml`).

### На prod
**Если пайплайн ничего не переопределяет — тоже по 1.**

Смотри пайплайн:
```yaml
.deploy:
  script:
    - helm upgrade --install boa "$CHART"
      --set imageRepo=...
      --set imageTag=...
      --set appVersion=...
      --set ingress.host="$HOST"
```

`--set replicas.frontend=...` нет. Значит, helm берёт **дефолт из `values.yaml`**, а там везде `1`.

То есть **staging и prod сейчас идентичны по репликам** — по одной каждого сервиса.

## Это правильно?

Для школьного проекта — **нормально**. Bank of Anthos в Школе 21 ничего не требует от тебя по высокой доступности.

**Но для красивого отчёта** есть смысл сделать prod «жирнее»: например, по 2 реплики на stateless-сервисы (frontend, balancereader, ledgerwriter, transactionhistory, userservice, contacts). Базы данных оставляем по 1 (они stateful, реплицируются иначе).

Если хочешь сделать **prod отличный от staging** — есть два пути:

### Путь 1. Через `--set` в пайплайне (быстро, без новых файлов)

В `deploy-prod` добавить:
```yaml
deploy-prod:
  extends: .deploy
  stage: prod
  variables:
    NS: prod
    HOST: bank.10.174.8.95.nip.io
  before_script:
    - export EXTRA_HELM_ARGS="--set replicas.frontend=2 --set replicas.userservice=2 --set replicas.contacts=2 --set replicas.balancereader=2 --set replicas.ledgerwriter=2 --set replicas.transactionhistory=2"
```

И в `.deploy` подхватывать `$EXTRA_HELM_ARGS`. Чуть громоздко.

### Путь 2. Через отдельные values-файлы (правильнее)

Создать два файла:
- `src/helm/bank-of-anthos/values-staging.yaml` — переопределения для staging (можно пустой)
- `src/helm/bank-of-anthos/values-prod.yaml` — переопределения для prod (больше реплик)

И в пайплайне:
```yaml
helm upgrade --install boa "$CHART" \
  -n "$NS" \
  -f "$CHART/values-$NS.yaml" \
  --set imageRepo=... \
  ...
```

Это профессиональный подход и хорошо смотрится в отчёте.
