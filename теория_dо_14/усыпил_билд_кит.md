Блок `tls` встал идеально — `tls` на 2 пробела, поля на 4. Чарт готов. Сначала усыпим то, что греет, потом включим HTTPS.

## Усыпить BuildKit и реестр (снять нагрузку)

`buildkitd` (печатный станок) и реестр нужны только во время сборки. Сейчас они просто занимают память — усыпим их в ноль реплик (контейнеры остановятся, но настройки и данные останутся):

```sh
export KUBECONFIG=~/.kube/do14-config

kubectl scale deploy/buildkitd -n buildkit --replicas=0
kubectl scale deploy/registry -n registry --replicas=0
```

`scale --replicas=0` — «останови все поды этого приложения, но само приложение оставь». Память освободится.

> Если имя деплоя реестра другое — проверь: `kubectl get deploy -n registry`. Если реестр у тебя не Deployment, а StatefulSet, скажи — дам правильную команду. И помни: усыплённый реестр нельзя будить только тогда, когда нужна сборка/деплой образов. Для возни с TLS он не нужен — образы уже в кластере на нодах.

Проверь, что уснули:
```sh
kubectl get pods -n buildkit
kubectl get pods -n registry
```
Должно быть пусто (или `Terminating` → потом пусто).

**Разбудить обратно** (когда снова понадобится сборка) — те же команды с `--replicas=1`:
```sh
# НЕ СЕЙЧАС, на будущее:
# kubectl scale deploy/buildkitd -n buildkit --replicas=1
# kubectl scale deploy/registry -n registry --replicas=1
```

> Ещё, если греет сильно: у тебя крутятся **два** окружения сразу — staging и prod (16 подов суммарно). Если для отладки TLS хватит одного, можешь временно усыпить лишнее. Но не обязательно — HTTPS включится и так.

Честный вердикт: **давать больше нельзя.** Смотри цифры — они тревожные:

```
Память: всего 15Gi, доступно 2,6Gi
Подкачка (своп): занято 1,9Gi из 4,0Gi
```

Расклад:
- Ноут уже занят на **12 из 15 ГБ**, свободно только **2.6 ГБ**.
- И самое плохое — **своп уже используется на 1.9 ГБ**. Это значит памяти уже не хватает *сейчас*, и Linux вынужден сбрасывать часть на диск (своп — медленная «запасная» память на диске). Отсюда и твой перегрев/тормоза.
- VM уже забрали ~7.6 ГБ (master 3.8 + воркеры по 1.9).

Если добавить воркерам памяти — её взять **неоткуда**. Ты залезешь ещё глубже в своп, ноут будет тормозить и греться сильнее, а не лучше. Это путь в обратную сторону.

То есть проблема не в том, что «мало отдал виртуалкам», а в том, что **физической памяти ноута (16 ГБ) впритык** на такой стенд (3 VM + Ubuntu + Chrome + твои приложения).

## Что реально поможет (без добавления RAM)

Раз памяти нет — надо **освободить** то, что занято зря. Варианты по эффективности:

**1. Усыпить то, что не нужно прямо сейчас (быстро, безопасно):**
```sh
export KUBECONFIG=~/.kube/do14-config
# buildkit и реестр нужны только при сборке — усыпить
kubectl scale deploy/buildkitd -n buildkit --replicas=0
kubectl scale deploy/registry -n registry --replicas=0
```
Освободит ~300-500 МБ. (Будить перед следующей сборкой.)

**2. Закрыть лишнее на самом ноуте** — Chrome с кучей вкладок легко ест 2-3 ГБ. Закрой ненужные вкладки/приложения. Это вернёт больше всего памяти, причём мгновенно.

**3. Если staging для текущих задач не нужен — временно усыпить его** (он дублирует prod, экономия ~半 подов):
```sh
# усыпить все сервисы staging (НЕ удаляя — потом вернёшь scale ...=1)
for d in $(kubectl get deploy -n staging -o name); do kubectl scale $d -n staging --replicas=0; done
```
Освободит заметно — staging это 8 подов. Вернуть: те же команды с `--replicas=1`.

> Почему не стоит добавлять RAM виртуалкам: ты бы взял память «в долг» у свопа, и кластер стал бы работать **медленнее**, а ноут горячее. Текущая раздача (4/2/2) под твои 16 ГБ — уже на грани разумного. Лучше разгрузить, чем раздуть.

## Честный итог

Для учебного стенда твой ноут на пределе, и это **нормально** — задание не требует мощного кластера, всё работает. Для отчёта это даже плюс: ты можешь честно написать «стенд ограничен 16 ГБ RAM хоста, поэтому prod-реплики масштабируются по требованию, а не постоянно» — грамотное инженерное обоснование, а не оправдание.

Если хочешь реально больше ресурсов под кластер — это уже про **другое железо**: либо твоя Fedora-рабочая станция (там 64 ГБ ECC — вот где развернуться!), либо VPS/облако. Но для сдачи ДО14 текущего стенда достаточно.

Мой совет: **не трогай память VM**, а усыпи buildkit+registry (п.1) и закрой лишние вкладки Chrome (п.2) — этого хватит, чтобы ноут вздохнул. Хочешь — дам команды, или на этом по ресурсам закончим и приберём кластер к сдаче?
