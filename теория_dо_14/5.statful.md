База данных — это классический Stateful (с сохранением состояния) сервис.
Главная задача любой базы данных — надежно сохранять, изменять и помнить информацию (то есть «состояние» системы) между запросами пользователей.
## Почему СУБД всегда Stateful:

* Постоянство данных: Если вы запишете строку в таблицу, база данных обязана «помнить» её при следующем запросе, даже если вы перезапустите сервер.
* Транзакции (ACID): База данных отслеживает промежуточные состояния данных (например, деньги уже списались с одного счета, но еще не дошли до другого), чтобы гарантировать корректность операции.
* Специфика масштабирования: В отличие от stateless-сервисов, нельзя просто запустить 10 копий базы данных для увеличения скорости. Придется настраивать сложную репликацию и синхронизацию, чтобы все копии «знали» одинаковое актуальное состояние.

## Важное исключение (базы данных в Docker/Kubernetes)
Иногда путаница возникает при контейнеризации. Сам контейнер с базой данных (например, PostgreSQL или MySQL) является stateful. Если удалить такой контейнер без подключенного внешнего диска (Persistent Volume), все сохраненные данные сотрутся.

Stateless (без состояния) и Stateful (с сохранением состояния) — это два разных подхода к архитектуре программных систем, которые определяют, помнит ли сервер историю общения с клиентом. [1, 2] 
Главное отличие заключается в том, где хранятся данные о текущем сеансе работы (сессии). [3, 4] 
------------------------------
## 1. Stateless-сервисы (Без состояния)
Такой сервис не хранит никакую информацию о предыдущих запросах пользователя на своем сервере. Каждый новый запрос обрабатывается с нуля, как будто клиент обратился впервые. [1, 5] 

* Как это работает: Клиент обязан передавать абсолютно все необходимые данные (контекст, токены авторизации, параметры) внутри каждого запроса. [1] 
* Аналогия из жизни: Торговый автомат. Вы бросаете монету и выбираете кофе. Автомату все равно, кто вы, и что вы покупали минуту назад. Ему важен только текущий запрос и монета в нем.
* Примеры:
* Большинство современных [REST API](https://javarush.com/groups/posts/68570-sostojanija-stateless-i-stateful-v-rest-api-) сервисов.
   * Поисковые системы (вы ввели запрос — получили результат).
   * Авторизация на базе JWT-токенов (сервер валидирует токен из заголовка, но не держит сессию в памяти). [1] 

## 2. Stateful-сервисы (С состоянием)
Такой сервис запоминает контекст общения и сохраняет данные о состоянии пользователя между запросами. [2] 

* Как это работает: Сервер создает сессию для клиента и сохраняет её в своей памяти или базе данных. Клиенту обычно выдается только короткий идентификатор (Session ID). При следующем запросе сервер по этому ID «вспоминает» историю взаимодействия. [1, 2, 3] 
* Аналогия из жизни: Официант в любимом ресторане. Он помнит ваше имя, ваши предпочтения, что вы заказали на закуску и приносит горячее, опираясь на эту историю.
* Примеры:
* Классические интернет-магазины с корзиной на серверных сессиях.
   * Онлайн-игры (сервер должен постоянно знать точные координаты и инвентарь вашего персонажа).
   * Протоколы связи вроде FTP или SSH, где сессия поддерживается на протяжении всего подключения.

------------------------------
## Сравнение архитектур

| Критерий [1, 2, 3] | Stateless (Без состояния) | Stateful (С состоянием) |
|---|---|---|
| Хранение сессии | У клиента (в запросе) | На сервере (в памяти/БД) |
| Масштабирование | Очень легкое (любой сервер ответит на запрос) | Сложное (нужно синхронизировать сессии между серверами) |
| Отказоустойчивость | Высокая (если сервер упадет, запрос обработает другой) | Ниже (при падении сервера текущая сессия может пропасть) |
| Размер запроса | Больше (передаются все данные) | Меньше (передается только ID сессии) |

В современной веб-разработке и микросервисах чаще стремятся делать приложения Stateless, так как их гораздо проще масштабировать под высокой нагрузкой. [3]
