## Что мы сделали в этом чате

### Подход к секретам (важно!)

Прав на GitLab CI/CD Variables нет, поэтому секреты решили хранить **в кластере**, а не в GitLab. Логика та же, что в ДО12 с токеном раннера (передавали через Helm в кластер, не в GitLab Variables).

**Пайплайн написан в двух режимах** — сейчас работает на кластерных секретах, позже сокомандник поднимет «нормальный» GitLab и можно будет переключиться на CI/CD Variables без правки YAML (условия `if [ -n "$DOCKERHUB_TOKEN" ]` просто перестанут быть ложными).

### Конкретные действия

1. **Проверили раннер** — был жив, но получал 403 Forbidden (старый токен устарел).
2. **Создали namespace `prod`** (`staging` уже был).
3. **Создали RoleBinding'и** `gitlab-deployer-staging` и `gitlab-deployer-prod` с `ClusterRole=edit` для `ServiceAccount gitlab-runner:default` и `gitlab-runner:gitlab-runner` — чтобы поды заданий могли делать `helm upgrade` в эти namespace.
4. **Создали JWT-секреты** `jwt-key` в обоих namespace (`staging` уже был с ДО13, в `prod` создали новый из файлов `jwtRS256.key` и `jwtRS256.key.pub`, которые лежат в `helm/bank-of-anthos/`).
5. **Создали Kubernetes Secret `dockerhub-auth`** в namespace `gitlab-runner` через `kubectl create secret docker-registry` с логином Docker Hub и Personal Access Token (Read/Write).
6. **Обновили values раннера** — добавили в `runners.config` блок:
   ```toml
   [[runners.kubernetes.volumes.secret]]
     name = "dockerhub-auth"
     mount_path = "/kaniko/.docker"
     read_only = true
     [runners.kubernetes.volumes.secret.items]
       ".dockerconfigjson" = "config.json"
   ```
   И сделали `helm upgrade gitlab-runner gitlab/gitlab-runner -n gitlab-runner -f /tmp/runner-values.yaml`.
7. **Поменяли регистрационный токен раннера** на новый — 403 ушёл.

### Файл пайплайна

Лежит в `~/до_14/DO14/src/.gitlab-ci.yml`. Внутри 4 стадии: `build → test → staging → prod`.
- **build:** Kaniko + `parallel:matrix` собирает 8 образов, пушит в `docker.io/$DOCKERHUB_USER/$SERVICE:$IMAGE_TAG` (тег = `CI_COMMIT_SHORT_SHA`) и `:latest`. Авторизация — через примонтированный раннером `/kaniko/.docker/config.json`.
- **test:** `mvn test` для 3 Java-сервисов (balancereader, ledgerwriter, transactionhistory) и `pytest` для 2 Python (userservice, contacts).
- **staging:** `helm upgrade --install boa $CHART -n staging` с `--set imageRepo=docker.io/$DOCKERHUB_USER --set imageTag=$IMAGE_TAG --set ingress.host=bank-staging.10.174.8.95.nip.io`.
- **prod:** то же, но в `prod` namespace и `when: manual`.

В пайплайне `DOCKERHUB_USER` ещё **не заменён** на реальный логин (стоит `ЗАМЕНИ_НА_СВОЙ_ЛОГИН_DOCKERHUB`).

## Что НЕ сделано (следующие шаги)

1. **Заменить `DOCKERHUB_USER`** в `src/.gitlab-ci.yml` на реальный логин Docker Hub.
2. **Сказать GitLab, где искать конфиг** — Settings → CI/CD → General pipelines → CI/CD configuration file → `src/.gitlab-ci.yml` (если поля нет — переложить файл в корень репо).
3. **Запушить** в ветку `develop` и посмотреть на первый запуск.
4. **Опционально:** сделать prod отличным от staging (больше реплик через `values-prod.yaml` или `--set replicas.*`).
5. **НЕ нужно сейчас:** TLS через cert-manager — задание про CI/CD, не про сертификаты.

## Где какой секрет лежит

| Что | Где |
|---|---|
| Токен раннера | Kubernetes Secret `gitlab-runner` в ns `gitlab-runner` (создан Helm-чартом раннера) |
| Токен Docker Hub | Kubernetes Secret `dockerhub-auth` в ns `gitlab-runner`, монтируется в build-под |
| JWT-ключи | Kubernetes Secret `jwt-key` в ns `staging` и `prod`, чарт берёт его по имени |
| GitLab CI/CD Variables | **Не используем** — прав нет |

## Известные ограничения и нюансы

- Build пересобирает все 8 образов при каждом пуше (~15-20 минут). Кэширование Kaniko не настроено — для школьного проекта оставляем как есть.
- Реплики на staging и prod одинаковые (по 1) — не оптимизировали.
- Регистрационный токен раннера светится в `helm get values` — не публиковать вывод.
- Ingress без TLS — приложение ходит по HTTP, домен nip.io.
