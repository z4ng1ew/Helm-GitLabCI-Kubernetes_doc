Хороший вопрос — разберём по цепочке, потому что тут есть неочевидный момент: **раннер и кластер у тебя — это одно и то же место.**

## Где запускается staging-стейдж

Твой GitLab Runner установлен **внутри** кластера k3s (в namespace `gitlab-runner`), с Kubernetes-executor. Значит, когда срабатывает `staging-job`, GitLab создаёт под-исполнитель прямо в твоём кластере. Этот под — уже внутри k3s, ему не надо «куда-то снаружи подключаться к кластеру», он там и живёт.

## Что делает сам стейдж

Посмотри на `staging-job` из твоего `.gitlab-ci.yml` по шагам:

```yaml
before_script:
  - curl -LO ".../kubectl"   # скачивает kubectl в под-исполнитель
  - mv kubectl /usr/local/bin/
script:
  - kubectl get nodes        # обращается к кластеру
  - helm upgrade --install my-hotels . --namespace hotels ...
```

Цепочка такая:

1. Образ стейджа — `alpine/helm:3.14.0` (в нём уже есть `helm`). В `before_script` докачивается `kubectl`.
2. Под-исполнитель запущен внутри кластера, поэтому у него **автоматически** есть доступ к API-серверу k3s через service account (служебную учётку пода). Именно поэтому `kubectl get nodes` и `helm upgrade` работают без явного kubeconfig — под изнутри кластера видит API-сервер по внутреннему адресу и аутентифицируется своим service account.
3. `helm upgrade --install my-hotels .` читает твой чарт (`src/hotels-app`, который раннер склонировал вместе с репозиторием) и **отправляет манифесты в API-сервер k3s**. API-сервер создаёт/обновляет Deployment'ы, Service'ы, Secret, ConfigMap — то есть разворачивает приложение в namespace `hotels`.

То есть staging не «куда-то выкладывает» — он прямо в том же кластере, где сам и крутится, говорит API-серверу «приведи namespace hotels к состоянию из этого чарта».

## Откуда у пода права на это

Ключевой момент — **RBAC** (Role-Based Access Control, управление доступом по ролям). Когда ты ставил раннер через Helm, в его `values.yaml` был блок:

```yaml
rbac:
  create: true
  rules:
    - resources: ["pods", "secrets", "configmaps", ...]
      verbs: ["get", "list", "create", "patch", "delete", ...]
```

Это создало служебной учётке раннера права на работу с ресурсами кластера. Благодаря им под-исполнитель может через `kubectl`/`helm` создавать поды, читать секреты и т.д. Без этих прав `helm upgrade` упал бы с ошибкой «Forbidden».

## Что насчёт секретов в staging

В стейдже есть ещё этот кусок:

```yaml
export POSTGRES_PASSWORD=$(kubectl get secret app-credentials -n gitlab-runner -o jsonpath='...' | base64 -d)
helm upgrade ... --set secrets.postgresPassword=$POSTGRES_PASSWORD
```

Под читает пароли из заранее созданного Secret `app-credentials` (в namespace `gitlab-runner`), расшифровывает из base64 и передаёт в `helm upgrade` через `--set`. Так пароли не лежат в `.gitlab-ci.yml` открытым текстом, а берутся из кластера в момент деплоя.

## Короткая схема

```
git push тега → GitLab запускает staging-job (вручную)
   → создаётся под-исполнитель ВНУТРИ k3s (namespace gitlab-runner)
      → под имеет права (RBAC) и доступ к API-серверу (service account)
         → helm upgrade отправляет чарт в API-сервер
            → API-сервер разворачивает приложение в namespace hotels
```

Один важный нюанс, который тебе пригодится на защите: это работает **только потому, что раннер внутри кластера**. Если бы раннер был на отдельной машине (например, GitLab.com), ему понадобился бы внешний доступ к API-серверу k3s и явный kubeconfig — а у тебя всё проще, раннер и кластер на одних виртуалках.

Хочешь — могу показать, как убедиться, что под-исполнитель реально имеет нужные права (проверить service account и RBAC раннера командой), или разобрать, почему staging срабатывает только на тег и вручную.
